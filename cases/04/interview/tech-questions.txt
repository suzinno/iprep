	What strategies do you use for zero-downtime schema migrations?
		(Expand-migrate-contract pattern. Add nullable columns first, backfill asynchronously, switch reads, then drop old columns later. Avoid long-running locks—use concurrent indexes. Always test on production-sized data snapshot.)
How do you evolve database schemas without downtime?
	(Use backward-compatible migrations: add columns nullable first, deploy code supporting both schemas, then backfill, then enforce constraints. For large tables, apply online DDL. Blue/green deployments help avoid locking. Rollback strategy must exist before migration runs.)

How do you balance read optimization with write performance?
	(Each index improves reads but slows inserts/updates. I measure write amplification impact before adding indexes. For heavy writes, I prefer covering indexes only for critical queries and archive historical data to reduce index size.)
How do you balance cost vs performance in data stores?
	(Hot paths in Redis/Dynamo, durable records in Postgres, and archival tiering in S3. I optimize for p95 first, then cost.)
What is PITR and when is it critical?
	(Point-in-time recovery restores DB to a specific timestamp using binlogs. Essential for accidental deletes or corruption scenarios.)
What are MongoDB sharding pitfalls?
	(Bad shard keys cause hotspots. Monotonically increasing keys break distribution. Also cross-shard aggregation is expensive. choose high-cardinality shard keys aligned with query patterns.)

How do you measure cache effectiveness?
	(Primary metric is hit rate per keyspace. Also monitor eviction rate and memory fragmentation. A high hit rate with high eviction suggests undersized memory or poor TTL strategy.)

How do you trigger Lambda from RDS events?
	(Direct DB triggers invoking Lambda are risky - can lead to performance bottlenecks, uncontrolled costs. - Prefer decoupled invoking between RDS and Lambda for resilience. Use SNS/SQS or CDC streams to decouple Lambda from direct DB triggers.)
	(Performance and Scalability Issues:
	- Database Connection Exhaustion: Lambda functions can scale up very rapidly. If a high volume of database changes occurs, each trigger can spawn a new Lambda instance, quickly exhausting the database's connection pool, causing the database to become unresponsive.
	- Latency Spikes: If the trigger is synchronous (waits for the Lambda to finish), the database transaction cannot finish until the Lambda function completes. If the Lambda is slow or experiences a cold start, the database performance suffers significantly.
	- Recursive Loops: If the Lambda function, acting upon the trigger, updates the same database table that triggered it, it creates an infinite loop of invocations, resulting in high costs and a potential denial-of-service condition. )

How do you decide on Sync vs. Async inter-service communication?
	(Critical, instant data consistency (e.g., bank transactions) requires synchronous calls. Eventual consistency is perfectly acceptable for asynchronous systems.)
How do you design retry and dead-letter strategies?
	(Retries use exponential backoff with limited attempts. Failed messages go to DLQ for inspection. Infinite retries create storms. Poison messages must be isolated. Monitoring DLQ growth helps detect systemic failures early.)
How do you choose exchange types? in RabbitMQ
	(Direct exchanges for command-style routing, topic exchanges for domain events, fanout for broadcast notifications. I avoid overusing topic wildcards as they complicate observability. Choice depends on routing flexibility vs predictability. Healthcare workflows prefer explicit routing to reduce ambiguity.)
What are RabbitMQ clustering trade-offs?
	(Mirrored queues improve HA but reduce throughput. Network partitions cause split-brain risks. Quorum queues are safer but heavier. Monitor disk I/O closely.)
How do RabbitMQ consumers impact PostgreSQL performance under load? How to deal?
	(Burst consumers can overwhelm DB connection pool. - throttle consumer concurrency and use connection pooling (PgBouncer). Implement backpressure via queue prefetch limits.)

What replication factor do you choose when configuring Kafka and why?
	(Minimum 3 for production. Allows one broker failure without data loss. Balance between durability and storage cost.)
How does Kafka replication actually work at the broker level?
	(Each partition has a leader and followers. Followers replicate data from the leader and stay in the ISR (in-sync replica) set if they keep up. Producers with acks=all require writes to be committed by all ISR members before acknowledgment. If a follower falls behind, it leaves ISR. Leader election chooses a new leader from ISR to avoid data loss.)
What guarantees does a Kafka consumer group provide and what it does NOT guarantee?
	(Consumer groups ensure per-partition exclusivity and scalability, but not global ordering or automatic exactly-once delivery. Offset management is key.)
